# M6 plan — Will I make my flight?

## Running the passenger journey

Open source notebook `12_passenger_journey` after publishing a twin minute. Supply its full `push_id`, a `flight_id` from that twin run, integer seed and trial count (default 10,000). The optional `journey_policy` object overrides values in `Policy`; on Databricks enter it as JSON in the widget. The notebook reads the publication's frozen security reading and time-travels the flights table. It writes one MLflow child run and two Delta tables in the configured namespace. The App principal needs SELECT on `journey_experiments` and access to that experiment. The local query gateway and App must use the same revision of the shared package.

In the App select the source scenario and minute, click **Explore this minute**, then choose the flight/run, checkpoint, bag and stops. Each experiment covers 16 profiles with matched draws under baseline staffing and one extra lane assigned to the selected checkpoint. Each Delta trial row stores the six component durations. Toggle stops to include or exclude their recorded durations. The summary stores counts, five-minute bins, quantiles, sampling intervals and the first trial of each profile for playback.

The existing Three.js scene plays that trial at 60× speed. The passenger approaches the checkpoint, waits, screens, visits selected stops and walks to the published gate. Bag drop, coffee and restroom positions are illustrative. The two queue lengths are an assumed split of the published total, and the simulated services use synthetic bounded triangular distributions. The App shows the active policy. Direct USD loading is a possible future asset workflow.

## Original implementation plan

For a passenger entering the terminal at one published replay minute, estimate the chance of reaching a chosen gate by boarding close. Compare the staffed checkpoint with one additional lane under the same passenger and queue conditions. This is a synthetic planning scenario. Its probabilities depend on the service assumptions.

## 1. Freeze the decision

Start from the browser replay's exact source run, push ID, step and timestamp. Resolve the publication manifest and pinned Delta versions. Read SECURITY.queue_len at that minute and the selected flight's scheduled departure for that run. Persist the values, units, source identifiers, versions and manifest digest with the experiment. If the publication cannot identify the historical schedule or queue, mark it unavailable and create a new eligible publication for the demo. Never borrow a value from a newer replay.

Use terminal entry at the snapshot timestamp. Default boarding close to scheduled departure minus 15 minutes, per the backlog. Admit an updated cutoff only if its effective value and publication time can be shown as of entry. Exclude actual departure and subsequent replay minutes. Count gate arrival exactly at close as success. Record signed seconds to close for each trial.

## 2. Specify the journey and the staffing intervention

Start with one selected flight and explicit checked-bag, coffee and restroom choices. Publish a versioned Delta policy with named stage distributions, units, bounds and rationale. For the first fixture, use bounded triangular durations in seconds for bag-drop elapsed time (including its wait), security service, gate walking and each optional stop. Record the three distribution parameters for every stage. Use zero for skipped stages. Bag-drop timing needs its own assumption because the existing baggage signal describes arriving luggage.

For the first model, treat the published queue as the number ahead when the passenger reaches security, even after bag drop. State this static-queue approximation in the App. Serve those passengers first-come, first-served on identical lanes, all initially available, assigning each passenger to the next free lane. Include the focal passenger's screening time. Set the baseline lane count in policy and open one additional lane immediately in the comparison. Queue evolution, lane startup and arrivals overtaking the passenger are outside this first model.

Generate 10,000 paired trials as a proposed demo default. Derive independent, stable random streams by seed, trial and stage. Reuse the same service draws for every person ahead and the same focal passenger draws in both arms. Compare success rates in percentage points. Report simulation sampling uncertainty for each rate and the paired difference separately from uncertainty about the assumed service rates.

## 3. Persist and track the paired experiment

Add configurable UC Delta tables for policy versions, frozen experiment inputs, trial results and summaries. Key trial rows by experiment, arm and trial index. Store stage seconds, total seconds, deadline margin and success. Summaries carry counts, success probability, interval, p50/p90 journey time, common histogram bins and mean seconds by stage. Rank bottlenecks by mean contribution to elapsed time, separating security wait from screening.

Use one journey MLflow run per paired experiment, linked by parent twin run ID and exact publication ID. Log seed, trial count, policy values/hash, source versions, code identity, per-arm metrics and paired changes. Link the Delta inputs and result identifiers. Derive a reproducibility key from immutable inputs, model version and seed. Stage writes under an execution ID, verify counts for both arms, then mark the experiment complete. A retry must never expose partial or duplicated trials.

## 4. Deliver the browser comparison

Add a read-only journey panel to the existing replay App. Match completed experiments to the selected publication, flight and passenger choices. Show boarding close and minutes available above two success probabilities and their percentage-point difference. Plot both journey-time distributions on the same axis with the available-time cutoff. Below the chart, show bottlenecks in minutes, assumptions, trial count and links to the journey run and source publication. Clear prior results when replay selection changes. Show “No journey experiment for this minute” when appropriate.

## Implementation order and acceptance

1. Build a frozen-input reader and a small historical fixture. Change later queue readings and actual departure in the fixture and prove the decision inputs and outcomes stay identical. Exercise missing history and ambiguous flight selection.
2. Build the pure Python 3.11 engine. Verify a hand-computed queue, zero queue, skipped stops, deadline equality and already-closed boarding. Replay with the same seed and inputs. Assert an extra lane never increases wait on a paired trial under this policy. Allow zero improvement.
3. Add DDL, a shared runner and a thin source notebook using the existing configuration, Spark platform and MLflow helpers. Exercise retry after one arm writes, verify Delta-to-MLflow lineage and measure the local 10,000-pair run against the existing two-minute filming target.
4. Extend the existing App data adapters and frontend. Browser-test a saved pair, cutoff and units, an empty minute and rapid replay switching. Reconcile displayed values to the persisted summaries. Rehearse one publication with a meaningful deadline near the journey distribution and record its IDs before filming.
5. Run local integration with the pinned Python environment. Validate packaging and both configuration paths. Real Databricks execution and deployment require separate approval. Use the same engine, notebook and App across targets.
